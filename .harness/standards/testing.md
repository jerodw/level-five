# Testing Standards

- Tests live in `tests/` and run with `.venv/bin/python -m pytest tests/ -q -n auto`, which is `test_command` in `.harness/config.yaml` verbatim — the harness's own gates run that command, so a developer's invocation and a gate's are the same one. `-n auto` reads the machine's core count rather than naming a number.
- The dependencies that command needs are declared in `requirements-dev.txt`, and it must be installed into both `.venv` and `.venv310` — the interpreter a developer runs the suite in and the one `verification_runner` names. Installed into only the first, the local suite is green and the clean-clone check dies on an unrecognized argument.
- Deterministic coordinator logic (routing, state transitions, context assembly, rule enforcement) must be covered by unit tests that never invoke a model.
- Agent invocation is isolated behind `agent_runner.py` so tests can substitute a fake runner.
- A story is not complete until all existing tests pass plus the new tests written for the story.
- Tests must not weaken or skip existing assertions to pass; verification rules are immutable.
- A test may bound how slow an *operation* is allowed to be, and may not bound how slow the *machine* is allowed to be. A command asked to sleep far past a configured timeout must be killed at that timeout — a loaded machine only makes that more true, so the assertion is about the harness. An assertion that a real operation *finished* inside a wall-clock window is a claim about the hardware at that moment, and under the parallel `test_command` above it is the claim that ends runs.
- Where such a window is a *precondition* rather than the question the test exists to ask — a child that must have been spawned before anything can be asked about the kill reaching its group, a session that must have written its artifact before anything can be measured from it — the test reports `tests/machine_load.py`'s `inconclusive(reason)` and nothing else. That is the only route: `tests/test_no_test_bounds_the_machine.py` reddens on a module under `tests/` that calls `pytest.skip` for a machine-load reason by any other one, and on a module that starts reading a clock without being classified there.
- This is not the weakening the rule above forbids, and the difference is which side of the question the test stopped on. A test that reached its question and declined to answer it is the forbidden thing. A test that never reached its question has an unmet precondition to report, and reporting it as a failure says something false — that the code is broken when what happened is that the run could not be conducted. No assertion is deleted for it, and the census, which refuses a stage whose assertion count fell, is what holds the difference.
- Widening a constant is not the remedy — a bound widened to five seconds is the same defect with a better number. Where a test has a load-independent half and a load-sensitive one, split them, so the half that proves the thing cannot be skipped by the other's precondition.
- A skip that can go quietly missing is worthless, so the route is bounded: `MAX_INCONCLUSIVE` in `tests/machine_load.py` is the most a run may report, counted once on the xdist controller over every worker's reports, and a run past it exits non-zero naming each one. A suite that proved nothing because the machine was too loaded is a failure rather than a pass. A declared `skip` or `skipif` marker carries no prefix and does not spend the ceiling.
